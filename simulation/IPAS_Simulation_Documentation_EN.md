# IPAS — Intelligent Pollution Analytic System
## ROS 2 Simulation — Developer Documentation

**Last updated:** 2026-08-22
**Environment:** ROS 2 Lyrical (Ubuntu 26.04 "Resolute")
**Project directory:** `~/GitHub_repose/IPAS/Simulation`

---

## 1. Overview

This document describes the current, working state of the IPAS
(Intelligent Pollution Analytic System) ROS 2 simulation. The goal is
to simulate the behavior of a real ESP32 + BME680 measurement system
under ROS 2, publish the data on a topic, persist it to disk, and
finally display it live on a web dashboard.

The system currently uses **entirely simulated data** — no real
hardware is connected. The `bme680_node` generates randomly fluctuating
but realistic values around a set of base values.

## 3. ROS 2 packages

### 3.1 `ipas_interfaces`

Interface package defining the single custom message type.

**`msg/IPASMeasurement.msg`:**
```
float32 temperature
float32 humidity
float32 pressure
float32 gas_resistance
```

> Note: the message currently has **no `Header`** (timestamp field).
> This is a deliberately open item — the timestamp is currently
> generated by the `ipas_logger` node at save time, not carried by the
> message itself.

**Build type:** `ament_cmake` + `rosidl_generate_interfaces`.

### 3.2 `ipas_bme680`

The node that simulates the BME680 sensor.

- **Node name:** `bme680_node`
- **Publishes:** `/ipas/measurement` (type: `ipas_interfaces/msg/IPASMeasurement`)
- **Update rate:** 1 Hz (`create_timer(1.0, ...)`)
- **Data generation:** random fluctuation around base values
  (`random.uniform`), not real sensor data:
  - `temperature`: 24.5 °C ± 0.5
  - `humidity`: 48.0 % ± 2.0
  - `pressure`: 1013.2 hPa ± 1.5
  - `gas_resistance`: 12000 Ω ± 500

**Start:**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source install/setup.bash
ros2 run ipas_bme680 bme680_node
```

### 3.3 `ipas_logger`

Subscriber node that logs every incoming measurement to a file.

- **Node name:** `ipas_logger_node`
- **Subscribes to:** `/ipas/measurement`
- **Output file:** `~/GitHub_repose/IPAS/Simulation/data/measurements.csv`
- **CSV columns:** `timestamp,temperature,humidity,pressure,gas_resistance`
- The timestamp is generated by the node itself (`datetime.now().isoformat()`)
  with microsecond precision — **no timezone designator** (naive, local
  time).

**Start:**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source install/setup.bash
ros2 run ipas_logger logger_node
```

## 4. rosbridge_suite — WebSocket bridge

A browser cannot subscribe to a ROS 2 topic directly, so `rosbridge_suite`
is used as the bridge.

**Installed package:** `ros-lyrical-rosbridge-suite` (4.2.1)

**Start — IMPORTANT: both `source` commands must run, in this order:**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source /opt/ros/lyrical/setup.bash
source install/setup.bash
ros2 launch rosbridge_server rosbridge_websocket_launch.xml
```

> If only the system ROS 2 environment is sourced
> (`/opt/ros/lyrical/setup.bash`) but not the local workspace
> (`install/setup.bash`), rosbridge fails to find the `ipas_interfaces`
> package and errors out with:
> `Unable to import ipas_interfaces.msg from package ipas_interfaces`.

**Port:** `9090` (WebSocket), listening on both IPv4 and IPv6.

## 5. Web dashboard integration

The dashboard's source file
(`~/GitHub_repose/IPAS/software/webpage/ipas_webpage.html`) is left
**untouched** — it is the original design/prototype. The ROS
integration is done on a **copy**:

```
~/GitHub_repose/IPAS/Simulation/web/
├── ipas_webpage_live.html   (live, ROS-connected version)
└── roslib.min.js            (local roslibjs library, v1.3.0)
```

> **Why a local file instead of a CDN?** The `roslib.min.js` URL on
> `cdnjs.cloudflare.com` did not serve valid content (a MIME type
> mismatch / HTML error page was returned instead of JS). Because of
> this, a verified `roslib.min.js` downloaded from the official npm
> package (`roslib@1.3.0`) is stored locally — this is also more
> robust, removing a network dependency from running the simulation.

### 5.1 Live components (fed from the `/ipas/measurement` topic)

| Dashboard element | Status | Source |
|---|---|---|
| **01 Current Conditions** cards (Temperature, Humidity, Pressure, Air Quality) | ✅ Live | `/ipas/measurement` (rosbridge WebSocket) |
| **ONLINE/OFFLINE** status | ✅ Live | WebSocket connection + 10s timeout |
| **02 Measurement History** graph | ✅ Live | `data/measurements.csv` (HTTP fetch, refreshed every 5s) |
| **03 Pressure — current value** (large number) | ✅ Live | `/ipas/measurement` |
| **03 Pressure — trend/delta/graph** | ⚠️ Simulated | pre-generated, static series |
| **04 Official Data Comparison** (table + radar chart) | ✅ Live (IPAS side) | `measurementData` object |
| **04 Official Data** (reference column) | Simulated (fixed) | `officialData` object — this represents the official reference station's data, currently a hardcoded constant |

### 5.2 ONLINE/OFFLINE logic

- Every incoming `/ipas/measurement` message calls `markOnline()`,
  which resets a 10-second timer.
- If no new message arrives within 10 seconds, the UI automatically
  switches to **OFFLINE** (`markOffline()`).
- If the WebSocket connection itself drops (`ros.on('close')`) or
  errors (`ros.on('error')`), the UI immediately reports OFFLINE.

### 5.3 Air quality (VOC) categorization

The BME680 only provides `gas_resistance` (Ω); there is no built-in VOC
index. The category shown on the card is derived from the
`gas_resistance` value expressed in kΩ:

| Category | Range (kΩ) |
|---|---|
| Excellent | > 150 |
| Good | 50 – 150 |
| Moderate | 15 – 50 |
| Poor | 5 – 15 |
| Very poor | < 5 |

For the **04 Official Comparison** chart, a numeric 0–100 scale index
is also computed (linear mapping: 200 kΩ → 100, 0 kΩ → 0), since the
radar chart and table expect a numeric value. This is a simplified,
prototype-level approximation that can be refined later.

## 6. Running the full system — step by step

Testing requires **five parallel terminals** (each with the correct ROS
2 environment sourced):

**Terminal 1 — rosbridge (WebSocket bridge):**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source /opt/ros/lyrical/setup.bash
source install/setup.bash
ros2 launch rosbridge_server rosbridge_websocket_launch.xml
```

**Terminal 2 — simulated BME680 sensor node:**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source install/setup.bash
ros2 run ipas_bme680 bme680_node
```

**Terminal 3 — data logger node:**
```bash
cd ~/GitHub_repose/IPAS/Simulation
source install/setup.bash
ros2 run ipas_logger logger_node
```

**Terminal 4 — local HTTP server (required for the dashboard to read the CSV):**
```bash
cd ~/GitHub_repose/IPAS/Simulation
python3 -m http.server 8080
```

**Browser:**
```
http://localhost:8080/web/ipas_webpage_live.html
```

> The dashboard must **not** be opened as `file://`, because browser
> security rules prevent `fetch()` (used to read the CSV) from working
> against the local filesystem — it only works over HTTP.

### Verification checkpoints

```bash
ros2 node list
# Expected: /bme680_node, /ipas_logger_node, /rosbridge_websocket, /rosapi

ros2 topic info /ipas/measurement
# Expected: Type: ipas_interfaces/msg/IPASMeasurement, Publisher count: 1

cat ~/GitHub_repose/IPAS/Simulation/data/measurements.csv
# Expected: header row + continuously growing data rows
```

In the browser, `F12` → Console tab should show:
`[IPAS] Connected to rosbridge at ws://localhost:9090`
with no red errors.

## 8. Known limitations and next steps

1. **No real hardware** — all data is simulated in `bme680_node`.
2. **No `Header` in `IPASMeasurement.msg`** — the timestamp currently
   only exists on the logger side, not as part of the message.
3. **The pressure trend chart (section 03) and the `+/− hPa / 6h`
   delta value remain simulated** — only the large, current-value
   number (`pressure-current`) is live so far.
4. **The "Official Data" (`officialData`) reference values are fixed,
   hardcoded** — there is no real official API integration yet.
5. **Browser-side CSV history reading has a fixed cap**
   (`MAX_HISTORY_POINTS = 60` rows) — this is not yet optimized for
   handling long-term, large-volume data.
6. **Timestamp timezone handling is not exact** — the CSV stores naive
   local time, and the browser's JS `Date` parser may interpret this
   under a different timezone assumption (minor, cosmetic discrepancies
   possible in the graph's time labels).
7. **No authentication / access control** on the rosbridge WebSocket
   endpoint — this is intended for a development/lab environment, not
   a production-grade security posture.
